# TitaniumPolitics Agent Guide

## Project map

- `core/` holds the game rules, simulation, save/load model, UI stages, and `GameAction` implementations.
- `lwjgl3/` is the main desktop launcher (`Lwjgl3Launcher`); `headless/` runs the scripted simulation (
  `TestEntryClass`).
- Runtime content lives in `assets/`; `ReadOnly` loads `assets/json/*.json` and `assets/texts/*.properties`.

## Architecture to understand first

- `GameState` is the serialized source of truth for characters, places, parties, meetings, requests, and info.
- `GameState.initialize()` builds a new world; `injectDependency()` reconnects deserialized objects to `parent`,
  `GameDataHandler`, and `Logger`.
- `GameEngine.gameLoop()` advances time, runs each character, then applies hourly/daily/quarterly progression.
- `GameAction` subclasses are serialized, validated with `isValid()`, then executed through
  `GameEngine.performAction()`.

## Cross-component communication patterns

- UI updates flow through `GameEngineThreadHandler` and `Gdx.app.postRunnable { ... }` to avoid touching LibGDX state
  off-thread.
- Player-facing text should come from `ReadOnly.prop/charProp/placeProp/script`, not hardcoded strings, because
  localization is bundle-driven.
- Many UI and app entry points use singleton `instance` fields (`EntryClass`, `MainMenu`, `LogUI`, etc.); reuse that
  pattern when wiring new screens.

## Persistence and data output

- Saves are written to `workingDirectory` by `GameState.dump()` / `dumpTemp()`.
- Per-turn telemetry is written by `GameDataHandler` into CSV files under the run directory (for example
  `temperature.csv`, `health.csv`).
- Most runtime model classes are `kotlinx.serialization`-friendly; keep non-serializable references marked `@Transient`.

## Conventions that matter here

- Kotlin sources often live under `src/main/java`; follow the package declarations (`com.titaniumPolitics.game.*`)
  rather than folder names.
- `ReadOnly` is the central place for constants, JSON loading, and locale selection; asset data such as
  `json/init.json`, `json/consts.json`, and `texts/*.properties` drive behavior.
- `assets/assets.txt` is generated by Gradle (`generateAssetList`); do not hand-edit it.
- The codebase favors large domain classes (`GameState`, `GameEngine`, `Character`, `Place`, `Party`) plus many focused
  `GameAction` classes in `core/.../gameActions/`.

## Developer workflow

- Only Build for final testing; for iterative development, use `./gradlew classes` to compile just the changed files.
- Compile/validate with `./gradlew build` or `./gradlew classes` for a faster check.
- Run the desktop app with `./gradlew lwjgl3:run` only if necessary to test graphics; run the headless integration path
  with `./gradlew :headless:run` for faster iteration on simulation logic.
- `core/src/test/kotlin/IntegratedTest.kt` is the main automated integration check; there are few isolated unit tests.
- When changing simulation logic, inspect `GameState.kt`, `GameEngine.kt`, `ReadOnly.kt`, and the relevant action/UI
  files together.
